# SPEC.md — 사진 끝말잇기 게임 규칙 룰북

> 이 문서는 게임 로직의 **불변 규칙**을 정의합니다.
> CLAUDE.md(진행 상황 로그), PHASES.md(개발 로드맵)와는 별도로 관리하며,
> 여기 적힌 규칙은 구현 시 반드시 따라야 하는 기준입니다.
> 규칙이 바뀌면 이 문서를 먼저 수정한 뒤 코드를 고칩니다 (스펙 우선).

버전: v0.8

## 1. 턴(Turn) 상태 머신

한 턴 = 사진 1장 + 그 사진에 등록된 정답 목록.

### 상태값

| 상태 | 의미 |
|---|---|
| `OPEN` | 사진이 올라왔고, 아직 아무도 정답을 맞히지 못한 상태 |
| `SOLVED` | 누군가 정답을 맞혀서, 어떤 정답으로 통과했는지(`matched_answer_id`)와 다음 시작 글자가 확정된 상태 |
| `INVALID` | 억지 신고에 대해 접속자 전원이 10초 내 동의하여 무효 딱지가 붙은 상태 |

### 상태 전이

```
OPEN ──(정답 제출 성공)──▶ SOLVED
SOLVED ──(10초 내 접속자 전원 동의)──▶ INVALID
```

- `OPEN → SOLVED`: 최초로 정답과 일치하는 답을 제출한 시도만 인정한다.
- `SOLVED → INVALID`: 무효 처리되어도 **이후 턴 데이터는 물리적으로 삭제하지 않는다.** 무효 딱지만 붙이고, 새 턴은 무효 턴의 **직전 SOLVED 턴의 끝 글자**를 기준으로 다시 이어간다 (분기 처리, MVP 기준). 세부 규칙은 5절 참고.
- `INVALID` 상태에서 되돌아가는 전이는 없다 (MVP 범위에서는 재투표/취소 없음).

### 동시성 규칙 (기술적 안전장치)

기획상 턴은 순차적으로 진행되지만(한 시점에 유효한 `OPEN` 턴은 체인 끝에 최대 1개), 여러 사용자가 동시에 같은 `OPEN` 턴에 정답을 제출할 수 있으므로:

- **한 턴은 정확히 한 번만 `OPEN → SOLVED`로 전이될 수 있다.**
- DB 레벨에서 이 전이를 원자적으로 보장한다 (예: `turns` 테이블에 상태 조건부 update, 또는 unique 제약으로 중복 SOLVED 방지).
- 늦게 도착한 제출은 정답 여부와 무관하게 **"이미 다른 사람이 맞혔습니다"** 로 처리한다.

### 1-1. 턴 생성(제출) 권한 — 고정 순번제

- 방에 실시간(비동기) 참여하는 사용자는 **방 최초 입장 시각(joined_at) 순서로 고정된
  순번**을 부여받는다. 순번 결정 방식은 방을 나갔다 다시 들어와도 바뀌지 않는다
  (최초 입장 시각 1회만 기록). `room_members` 테이블에 (room_id, user_id, joined_at)로
  기록하며, 재입장 시 upsert하되 joined_at은 갱신하지 않는다.
- 방 멤버를 joined_at 오름차순으로 0번부터 인덱싱했을 때, N명 중 **턴 번호 k를 생성할
  권한은 인덱스 `(k-1) mod N`인 멤버에게만 있다.** (`get_turn_holder` 함수가 판정)
- 순번이 아닌 사람이 제출을 시도하면 `not_your_turn` 오류로 거부한다. 이 판정도
  API 단(RPC)에서 원자적으로 강제한다.
- 순번인 사람이 응답하지 않으면 게임은 그 턴에서 **무기한 정지**된다. 별도의 타임아웃/
  자동 스킵 로직은 두지 않는다 (MVP 결정, 필요 시 Phase 11에서 재검토 가능).
- 첫 턴(turn_number=1)도 예외 없이 이 규칙을 따른다 — 인덱스 0번(방에 가장 먼저
  입장한 사람)만 자유 주제로 시작할 수 있다.
- 자기 자신이 올린 OPEN 턴은 자기 자신이 풀 수 없다(1-2절과 동일). 멤버가 1명뿐인
  방은 턴2부터 이 조건과 순번 조건이 충돌해 진행이 막히는 **알려진 한계**로 남겨둔다
  (최소 2명 입장 필요). 프론트는 멤버가 1명일 때 "2명 이상 입장해야 이어갈 수 있음" 안내를 표시한다.
- `(room_id, turn_number)` 유일 제약으로 동시 제출 레이스를 최종 방어한다.

### 1-2. 턴 제출의 원자적 통합

한 번의 턴 제출은 세 가지를 동시에 수행하는 **단일 원자적 행위**다:

1. 직전 OPEN 턴의 사진에 대한 **추측 제출** (이전 사진이 무엇인지 맞히기)
2. 자신의 **사진 업로드**
3. 그 사진의 **정답 등록**

- 이 셋은 하나로 묶여 처리되며, 중간 상태(맞혔지만 사진을 올리지 않은 상태)는 존재하지 않는다.
- **추측이 오답이면 어떤 것도 저장되지 않는다.** 사진 파일 업로드 자체를 수행하지 않으며,
  오답 시도만 `turn_attempts`에 기록된다 (오답으로 인한 고아 Storage 파일 방지).
- **추측이 정답이면** 같은 트랜잭션 안에서 직전 턴이 `SOLVED`로 전이되고, 새 턴과 정답이 생성된다.
- **첫 턴(turn_number=1)** 은 추측 대상이 없으므로 사진+정답만 등록하며, 시작 글자 제한도 없다
  (1-1절에 따라 순번 0번만 제출 가능).
- UX상 사전 검증(`check_guess`로 추측만 먼저 확인)을 제공할 수 있으나, **최종 판정은 반드시
  제출 시점의 단일 RPC(`submit_turn`) 안에서 다시 이루어진다** (프론트 사전 검증만 믿지 않는다
  — 4절/1-1절과 동일 원칙).

### 1-3. 오답 제한과 게임 종료 (하트 시스템)

- **각 사용자는 자기 턴에서 오답을 최대 3회까지 제출할 수 있다** (하트 3개). 하트 카운트는
  **각 사람의 각 턴마다 3개로 리셋**된다 (누적이 아니라 그 턴 한정).
- 3회를 모두 소진하면(3번째 오답) **게임이 종료**된다.
  - 3번 틀린 사람이 **패배**, 나머지 참여자는 **승리**로 처리한다.
  - 게임 종료 시, 못 맞힌 그 OPEN 턴의 **대표 정답(첫 번째 등록 정답, 2절 참고)이 공개**된다.
- 게임 종료 후 방은 물리 삭제하지 않고 **종료 상태로 유지**한다. 방장이 **"다시 플레이하기"** 를
  누르면 대기실로 전환된다.
- **재시작 규칙**:
  - **기존 사슬은 그대로 유지**한다 (지금까지 이어온 사진들이 사라지지 않음).
  - **패배자가 새 순번 0번**이 되어, 게임 종료 시 공개된 **대표 정답의 끝 글자**부터 이어서 시작한다.
  - 이후 순번은 패배자(0번) → (나머지 멤버 joined_at 순) 순환으로 재계산된다.
- UI에는 하트(남은 기회)가 시각적으로 표시되며, 오답마다 하트가 하나씩 사라지는 것이 보이면 좋다.

## 2. 끝말 판정 규칙

### 대표 정답 / 보조 정답

- 한 사진에 정답을 여러 개 등록할 수 있다. **등록 순서상 첫 번째 정답이 "대표 정답"** 이다.
- **대표 정답의 용도**: 게임 종료(오답 3회) 시 공개되는 정답이자, 재시작 시 다음 시작 글자의
  기준점이다 (1-3절). 아무도 못 맞혀서 어떤 정답으로도 사슬이 안 이어진 상황에서만 기준 역할을 한다.
- **보조 정답(두 번째 이후)**: 맞히기 판정 시 정답으로 인정되는 허용 범위다.
- **정상 플레이 중 다음 시작 글자는 "맞힌 정답"의 끝 글자로 정해진다** (대표/보조 무관).
  예: 보조 정답 "자전차"를 맞히면 다음은 "차"로 시작. 대표 정답은 이 계산에 관여하지 않는다.

### 끝 글자 추출

- 정답 문자열에서 **마지막 글자(음절) 1개**를 끝 글자로 삼는다.
- 공백은 제거한 뒤 마지막 글자를 취한다. (예: "리듬 세상" → 끝 글자는 "상")
- 특수문자/숫자로 끝나는 정답은 등록 단계에서 막는다 (2절 하단 "정답 등록 제약" 참고).

### 두음법칙

- **적용함** (v0.5 결정, Phase 4 착수 직전 확정).
- 규칙(한글 맞춤법 제10~12항 기준): 이전 턴 정답의 끝 글자를 기준으로, 다음 턴은
  그 글자로 시작하는 단어뿐 아니라 두음법칙이 적용된 형태로 시작하는 단어도 인정한다.
  - 끝 글자의 초성이 ㄹ이고 중성이 이/야/여/예/요/유 계열(ㅣ,ㅑ,ㅕ,ㅖ,ㅛ,ㅠ)이면
    → ㄹ이 ㅇ으로 바뀐 형태도 허용 (예: "리" → "이"도 허용)
  - 끝 글자의 초성이 ㄹ이고 그 외 중성이면 → ㄹ이 ㄴ으로 바뀐 형태도 허용
    (예: "라" → "나"도 허용)
  - 끝 글자의 초성이 ㄴ이고 중성이 이/야/여/예/요/유 계열이면
    → ㄴ이 ㅇ으로 바뀐 형태도 허용 (예: "녀" → "여"도 허용)
  - 그 외 초성/중성 조합은 변환 대상 아님, 원래 글자만 허용
- 구현: 완성형 한글 유니코드 공식(초성 19/중성 21/종성 28)으로 음절을 분해해
  판정하는 순수 함수(`compute_start_chars`)로 구현 (하드코딩 매핑 테이블 방식 아님).
  맞히기(3절)와 시작 글자 강제(하단)에서 공통으로 재사용.
- 다음 턴이 시작할 수 있는 글자는 항상 "원래 글자" + "두음법칙 적용 형태(해당 시)"
  의 최대 2가지 집합으로 표현되며, 어느 쪽으로 시작해도 정답으로 인정한다.

### 정답 등록 제약 (업로더가 정답 입력 시)

- 정답은 1개 이상 등록해야 한다.
- 정답 문자열은 한글 음절로 끝나야 한다 (영문/숫자/기호로 끝나는 정답 등록 차단).
- 동일 사진에 완전히 같은 정답 문자열 중복 등록은 막는다.

### 시작 글자 강제

- 새 턴에 등록하는 정답 중 최소 1개는, 직전 `SOLVED` 턴에서 맞힌 정답 기준 허용 시작 글자 집합
  (원래 글자 + 두음법칙 적용 형태, 최대 2개)으로 시작해야 한다.
- 판정 함수는 맞히기(3절)에 쓰이는 두음법칙 순수 함수를 그대로 재사용한다 (중복 구현 금지).
- 이 강제도 API 단에서 이루어진다 (1-1절과 동일 원칙).

## 3. 맞히기 비교 규칙

사용자가 입력한 답을 정답 목록과 비교할 때:

1. 앞뒤 공백(trim) 제거
2. 문자열 중간 공백은 제거하지 않는다 (예: "리듬 세상" ≠ "리듬세상" — 정확히 일치해야 함)
3. 유니코드 정규화: **NFC로 정규화 후 비교** (자모 조합 방식 차이로 인한 오탐 방지)
4. 대소문자 구분: 한글은 해당 없음. 영문이 섞인 정답이 있을 경우 **대소문자 무시하고 비교**
5. 그 외 유사도 판정(오타 허용, AI 판정 등)은 **적용하지 않는다** — "규칙이 투명·예측 가능해야 한다"는 원칙을 그대로 따름

### 오답 제출

- **오답 제출은 자기 턴에서 최대 3회까지 허용한다** (1-3절 하트 시스템). 3회 소진 시 게임 종료.
- 모든 제출 시도(정답/오답 무관)는 기록으로 남긴다 (`turn_attempts`, 신고/통계 기능에 활용).

> v0.8 변경: 기존 "오답 무제한 허용"에서 "턴당 3회 제한"으로 개정 (1-3절 게임 종료 규칙 신설에 따름).

## 4. 정답 노출(스포일러 방지) 규칙

- 사진을 올린 사람이 등록한 **정답 목록 원문은, 해당 턴이 `SOLVED` 또는 `INVALID`가 되기 전까지 업로더 본인 외 누구에게도 노출되지 않는다.**
- 프론트엔드 화면 렌더링뿐 아니라 **API/쿼리 응답 단계에서도 차단**해야 한다 (개발자 도구로 네트워크 응답을 봐도 정답이 보이면 안 됨). 즉 RLS 또는 서버 사이드 필터링으로 처리하고, 프론트엔드 조건부 렌더링만으로 숨기지 않는다.
- `SOLVED` 이후에는 해당 턴의 **채택된 정답(`matched_answer_id`에 해당하는 것)만** 노출한다. 등록됐지만 채택되지 않은 나머지 정답 후보들은 계속 비공개로 둔다 (다음 문제로 재활용될 수 있으므로).
- **예외 — 게임 종료 시 대표 정답 공개**: 오답 3회로 게임이 종료되면(1-3절), 못 맞힌 OPEN 턴의 **대표 정답(첫 번째 등록 정답)만** 공개된다. 나머지 보조 정답은 계속 비공개다. 이 공개도 서버 사이드에서 통제한다.

## 5. 신고(억지 끝말) / 무효 처리 규칙 — 실시간 즉석 투표 방식

> "누적 참여자 만장일치제"를 폐기하고, **그 순간 접속 중인 사람들의 실시간 즉석 동의** 방식으로 처리한다. 신고는 과거 이력을 쌓아두는 방식이 아니라, 발생한 순간의 사회적 합의로 즉시 처리한다.

### 신고 흐름

1. 참여자 중 한 명이 특정 매칭 정답(해당 턴을 `SOLVED`로 만든 답)에 대해 **"억지 신고"** 버튼을 누른다.
2. 그 즉시, **해당 방에 실시간 접속(Presence) 중인 사용자 목록**을 스냅샷으로 고정한다.
   - 이 목록에서 **피신고자**(신고 대상 답을 제출한 사람 본인)는 제외한다.
   - 신고자 본인은 신고 행위 자체로 **자동 동의 1표**로 카운트된다.
3. 스냅샷에 포함된 **나머지 전원**이 **10초 이내**에 "동의"를 눌러야 한다.
4. 10초 안에 전원 동의가 모이면 → 즉시 `SOLVED → INVALID` 전이.
5. 10초 안에 전원 동의가 모이지 않으면(누구든 무응답 포함) → 이번 신고 시도는 **무산**된다.

### 자기 신고 금지

- 자기 자신이 제출해 통과된 답은 신고할 수 없다. 프론트단 조건만이 아니라 **서버/DB 단에서도 강제**한다 (4절 원칙과 동일). `reports` 테이블에 `CHECK (reported_by <> reported_user_id)` 제약으로 강제.

### 최소 인원 조건

- 신고 시점에 **신고자와 피신고자를 제외하고 접속 중인 사람이 0명**이면, 신고 자체를 시작할 수 없다 (동의를 구할 대상이 없으므로). UI에서는 "억지 신고" 버튼을 비활성화하거나 안내 문구로 처리한다. 이 조건은 `start_report` RPC 안에서도 재검증한다.

### 오프라인 참여자 처리

- 신고가 뜬 순간 **오프라인이었던 사람은 이번 신고 건에 참여할 수 없다.** 나중에 재접속해도 이미 지나간(성공했든 무산됐든) 신고 건에는 동의할 수 없다.
- 즉, 과거 활동 이력(사진 업로드/정답 제출 여부)은 신고 자격 판단에 더 이상 쓰이지 않는다. 오직 **신고가 발생한 그 순간의 실시간 접속 여부**만 본다.

### 신고 재시도

- 무산된 신고는 즉시 다시 시도할 수 있다. 별도의 쿨다운은 두지 않는다 (기본값 — 필요 시 재검토).
- 같은 턴에 대해 동시에 진행 중인 신고는 1건으로 제한한다 (`reports` 부분 유니크 인덱스: `status='pending'`일 때 turn_id 유일).

### 무효 처리 이후

- 1절과 동일하게 물리 삭제 없이 무효 딱지만 붙이고, 새 턴은 무효 턴의 **직전 SOLVED 턴 끝 글자**를 기준으로 분기하여 다시 잇는다.

### 구현 참고 (기술적 요구사항)

이 방식은 **Supabase Realtime의 Presence(접속자 목록 추적) + Broadcast(신고 알림 즉시 전파)** 기능이 필요하다.

- **Presence**: 방 채널에 접속 중인 사용자 목록을 실시간으로 추적한다.
- **Broadcast**: 신고 발생 시 그 방의 모든 접속자에게 즉시 알림을 전파하고, 10초 타이머가 시작된다.
- **10초 판정 주체**: **서버 사이드로 확정** (v0.6). 각 클라이언트가 개별적으로 타이머를 돌리는 방식은 조작·이탈(브라우저를 닫아버리는 경우 등)에 취약하므로 채택하지 않는다. 신고 시작 시점의 Presence 스냅샷(접속자 목록)을 클라이언트가 서버로 전달해 `reports` 테이블에 `required_voters`/`agreed_voters`/`expires_at`(신고 시각+10초)로 고정하고, 이후의 동의 수집·전원 동의 판정·시간 초과 판정은 전부 DB 함수(RPC)에서 원자적으로 처리한다. Edge Function 없이 Postgres 함수만으로 충분하다고 판단.
- 이 요구사항으로 인해, **Realtime 인프라 구축을 Phase 6보다 먼저(Phase 3 사슬 조회 단계) 준비**해두는 것으로 PHASES.md에 반영함.

**기술 검증 완료**: Supabase Realtime은 공식적으로 멀티플레이어 게임 상태 동기화를 지원 사례로 명시하고 있어 이 설계에 적합함을 확인함. 무료 플랜 기준 동시 접속 200명, 메시지당 256KB 한도는 신고 알림 같은 가벼운 텍스트 신호에는 문제가 없으며, 이 한도는 사진 파일(Storage로 별도 전송)과는 무관함. 다만 최근 프로덕션 환경에서 Presence 이벤트(sync/join/leave)가 간헐적으로 안 뜨는 사례가 보고된 바 있어, 탭 전환(visibilitychange) 시 재추적(re-track)하는 방어 코드를 넣어두는 것을 권장하며 Phase 6 구현 후 다중 브라우저로 10초 타이머 동작을 반드시 실제 검증해야 한다.

## 6. 방(Room) 관리 규칙

### 방장 / 참여자

- 방을 만든 사람(`rooms.created_by`)이 **방장**이다.
- **방 삭제**: 방장만 **"방 삭제"** 버튼으로 방을 삭제할 수 있다. 삭제 시 관련 데이터
  (turns/answers/turn_attempts/reports/room_members)는 FK `ON DELETE CASCADE`로 함께 정리되며,
  각 턴의 사진 파일도 Storage에서 함께 삭제된다 (`turns` DELETE 트리거로 `storage.objects`에서 제거).
- **방 나가기**: 참여자는 **"나가기"** 버튼으로 방에서 나갈 수 있다. 단, `room_members`의
  joined_at 기록은 남겨 순번을 보존한다 (재입장 시 순번 유지 — 1-1절).

### 감지 방식

- 방장의 삭제, 참여자의 나가기 모두 **명시적 버튼**으로만 처리한다. 브라우저 종료/접속 종료
  (Presence 이탈)를 나감으로 간주하지 않는다 (새로고침을 나감으로 오인하는 것을 방지).

## 7. 미정 사항 (Decision Log)

| 항목 | 현재 상태 | 재논의 시점 |
|---|---|---|

| 순번제 1명 방 한계 | 알려진 한계로 수용 (2명 이상 필요) | 필요 시 Phase 11 |
